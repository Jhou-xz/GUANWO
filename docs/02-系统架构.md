# 02 · 系统架构

## 1. 第一性原则

**确定性的计算和概率性的生成必须分开。**

排盘是天文历法计算，输入相同输出必然相同，错就是错。
解读是 LLM 生成，本质是概率，会幻觉。
把它们混在一层，等于让一个会胡说的东西去算需要绝对精确的东西。所以：**分层，用数据契约连接。**

## 2. 分层

```
┌─────────────────────────────────────────────┐
│  前端体验层  (UX — "体验拉满"主战场)            │
│  输入引导 · 命盘可视化 · 解读呈现 · 对话追问     │
└───────────────┬─────────────────────────────┘
                │ HTTP / 流式
┌───────────────▼─────────────────────────────┐
│  应用 / API 层                                │
│  鉴权 · 限流 · 会话 · 付费门 · 缓存            │
└──────┬──────────────────────────┬───────────┘
       │                          │
┌──────▼─────────┐      ┌─────────▼────────────┐
│  排盘引擎       │      │  AI 解读层            │
│  (确定性)       │ JSON │  (LLM)               │
│  八字 / 紫微    │─────▶│  人设 · RAG · 护栏    │
│  农历 · 节气    │ 命盘 │  对话 · 流式输出      │
└──────┬─────────┘      └─────────┬────────────┘
       │                          │
┌──────▼─────────┐      ┌─────────▼────────────┐
│  历法/星历依赖   │      │  命理知识库 (RAG)     │
│  lunar-ts 等    │      │  规则 / 古籍 / 释义    │
└────────────────┘      └──────────────────────┘
```

## 3. 模块职责

### 3.1 排盘引擎（core，最先做、最先稳）
- 纯函数：`生辰 + 选项 → 命盘JSON`，无副作用、无网络、可单测
- 子模块：历法转换 / 八字排盘 / 紫微排盘 / 神煞·大运·流年
- **不依赖 AI，不依赖网络**。可独立打包成库，CLI 可直接跑出盘
- 这是所有形态（小程序/App/Web）的共同地基

### 3.2 AI 解读层
- 输入：命盘 JSON + 用户问题 + 对话历史
- 流程：检索相关命理规则(RAG) → 组装 prompt → LLM 流式生成 → 护栏过滤
- **绝不做数学**：不算干支、不查农历、不数五行。这些都从 JSON 读
- 详见 [04-AI解读层](04-AI解读层.md)

### 3.3 应用/API 层
- 命盘缓存（同一生辰只算一次，结果稳定可缓存）
- 付费门控（哪段解读免费、哪段付费）
- 会话管理（对话式解读需要持久化上下文）

### 3.4 前端
- 形态待定，但引擎/AI 与前端解耦，前端可后换（小程序/App/Web 复用同一套 API）

## 4. 技术选型（建议，待拍板）

| 层 | 建议 | 理由 |
|---|---|---|
| 引擎语言 | **TypeScript** | 复用性最强：同一套可跑 Node 后端、Web、小程序；生态有 `lunar-typescript` |
| 历法库 | **lunar-typescript (6tail)** | 国内验证充分，覆盖阳历/农历/干支/节气/八字；避免自己写天文 |
| 紫微 | 现成库 or 在 lunar 农历数据上自实现安星 | 紫微库质量参差，可能需自实现+对账 |
| 七政四余 (v2) | **Swiss Ephemeris (swisseph)** | 需真实行星黄经，非历法库能给 |
| AI | **Claude（Opus/Sonnet）** | 中文质感、长上下文（整盘+对话）、指令遵循强 |
| RAG | 向量库 + 命理规则/古籍语料 | 让解读有据可依，减少幻觉 |
| 后端 | Node (与引擎同语言) | 减少跨语言序列化摩擦 |

> 选型原则：**引擎用 TS 是为了一份代码多端复用**。若后端选别的语言，引擎可独立成 TS 库通过子进程/WASM 调用，但增加复杂度，非必要不引入。

## 5. 数据流（一次完整解读）

1. 用户输入生辰（公历/农历、时辰、性别、出生地）
2. API 校验 → 查命盘缓存 → 未命中则调引擎
3. 引擎产出**命盘 JSON**（见 [05-命盘数据模型](05-命盘数据模型.md)）→ 缓存
4. 前端先渲染命盘可视化（即时、无需等 AI）
5. AI 解读层：RAG 检索 → prompt 组装 → 流式生成解读 → 护栏
6. 前端流式呈现 → 用户可追问 → 回到第 5 步（带对话历史）

## 6. 关键架构决策与理由

- **引擎与 AI 隔离**：保准确、保可测、保可缓存。
- **命盘 JSON 为唯一契约**：前端、AI、缓存都依赖它，schema 要先定稳。
- **引擎用纯函数**：可单测、可对账、可复现，是信誉的工程保障。
- **命盘可视化先于 AI 渲染**：用户秒见盘，AI 慢慢说，体验不卡。
- **合规护栏在 AI 层出口**：而非依赖模型自觉，详见 04。
