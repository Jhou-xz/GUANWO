# 05 · 命盘数据模型

> 这是整个系统**最重要的接口**：引擎产出它，AI/前端/缓存都消费它。
> schema 先定稳，再写代码。下面是草案（字段用中文 key 便于人读，落地可改英文 key）。

## 1. 设计原则

- **自包含**：AI 读这一份就够，不用回头查引擎
- **结构化到底**：藏干、十神、四化都拆成字段，别塞自然语言
- **带元信息**：记录用了哪些流派选择（真太阳时/子时规则），保证可复现、可解释
- **引擎不写解读**：JSON 里只有事实（盘是什么），没有判断（吉凶好坏）。判断是 AI 的活

## 5. 给 AI 的视图 vs 给前端的视图

- **同一份 JSON**，但用途不同：
  - **前端**：用它画命盘图（四柱排盘表 / 紫微十二宫圆盘）
  - **AI**：整份注入 context 做解读（可能再附 RAG 释义）
- 若 AI context 太长，可提供**精简视图**（去掉前端才需的可视化冗余字段），但事实字段不删

## 6. 契约纪律

- schema 改动 = 破坏性变更，要版本号（`"版本"` 字段）+ 引擎/AI/前端同步
- 引擎只写**事实**，不写**判断**（"身旺"是事实推论可留，"命好"这种判断不准进 JSON）
- 任何带流派色彩的字段（旺衰、神煞）标注依据/出处，供 AI 和用户追溯
- 这份 schema 一旦多端依赖就很难改，**MVP 前多花时间定稳它，值得**
